# PriceMap AI · AI 服务报价查询与比较

**把分散报价变成可发现、可解释、可回查的候选。**

个人续订 AI 服务，需要分清交付方式、期限与库存；开发者选 API，需要看懂模型、分组、币种和单位。我独立完成产品设计与工程交付，用两条查询路径组织原站数据。网站已上线，用户在站内缩小范围，再到原站确认；当前分类、换算与调度使用确定性规则。

## 两条实际查询任务

### 订阅：从目标产品核对交付条件

选择类别与产品，查看交付方式、期限和库存，再进入对应原站确认。充值、成品号和共享账号不是同一规格，目录起价也不等于符合用户条件的最低价。

![历史演示：订阅详情与原站入口](demo/assets/02-subscription-detail.jpg)

### API：从模型核对计费含义

选择平台或模型，再查看站点与分组，解释输入 / 输出单位、现金与余额额度、倍率及监测范围。综合系数不能替代用户实际工作负载的总成本。

## 三项设计，支持持续使用

![用户查询、后台生产与公开快照交付](demo/assets/architecture.svg)

**保留规格与金额语义。** 标题、比较键、单位、币种及倍率是否已应用分别保存，避免把额度当现金或重复换算；规格缺失时不强行输出同规格结论。

**将公开读取与采集分开。** React / Vite 前端读取版本化静态 JSON；Supabase 承担采集和报价库，Worker、Durable Object 与私有 R2 支持增量发布、校验和恢复。完整版本才交付，访问增长不逐次牵动数据库查询，但增加发布链路与时效管理。

**按需求与变化分配更新预算。** 关注、价格 / 库存变化和缺货来源分档更新，热点另行核验；日预算与断点恢复控制投入，也需要防止冷门来源长期得不到更新。[参数、换算示例与代价](docs/technical-design.md)

## 目录已有覆盖，严格比较仍待改善

2026-10-17 13:47（北京时间）的固定快照包含 4,822 条订阅报价、27 家 API 站点及 3,319 条 API 报价。订阅严格资格筛选只有 **6 条合格，0 个至少两家来源的可比组**；目录起价采用更宽规则。因此目录规模不代表已经具备充分的同规格比价能力。

离线回放还检验完整分页、版本、重复数据及有效期；它验证规则与交付，不能证明每个外站商品或模型身份。当前已有事件埋点，尚无可核验的任务完成、留存或成交统计。[公开快照与质量诊断](evaluation/README.md)

下一阶段优先统一价格标签、补齐高需求规格、抽查商品对应关系，再用真实查价任务观察理解错误与核对耗时。LLM 规格提取、工作负载计算和提醒能力属于条件规划，尚未作为线上能力交付。[需求池与演进](docs/product-design.md#需求池与当前顺序) · [任务指标与实验](docs/metrics-and-experiments.md)
