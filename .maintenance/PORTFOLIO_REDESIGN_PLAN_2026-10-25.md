# AI 产品作品集整体改版计划

日期：2026-10-25。状态：执行版；企业实践部分已按本轮公开边界修正，替代此前要求补机制图和企业原件的条款。整体结构沿用原方案，不再重新讨论分类或扩展文档体系。用户已授权正式执行；执行进度见 [ROADMAP](ROADMAP.md)，实际检查与待补材料见[本轮验收](REDESIGN_REVIEW_2026-10-25.md)。源码与历史原件保留，执行记录以实际检查为准。

## 1. 改版目标与判断依据

本次改版把仓库组织成能够独立阅读的产品与研究案例作品集。它可以用于求职、项目交流与合作；首页围绕作品组织，具体项目解释问题、方案、交付、验证和迭代。

简历承担个人身份、公司、职务、年月与职业经历的介绍；作品集展示可以检查的作品与思考过程。项目只保留理解作品所需的个人参与范围与职责；两个企业实践不提公司。

改版需要达到四个结果：

1. 打开首页，能迅速知道有哪六个作品、各自解决什么问题、目前做到哪一步、从哪里观看或阅读。
2. 进入任何一个案例，不读代码也能理解一次具体任务、关键方案和实际交付。
3. 深入查看时，重要判断能找到设计、真实产物、实验或实现依据。
4. 历史成果、当前实现、新增复盘和后续计划有清楚边界。

依据是本仓库当前六个项目、既有维护材料，以及 2026-10-25 对作品集定位的讨论。旧计划中的“三个项目”“不新增第四个”“不引入企业案例”“保持私有”等描述属于过去阶段，不能继续当作当前全仓库约束。当前已有六个项目；10 月 25 日只读检查显示远端为公开仓库。本计划不改变远端公开状态。

## 2. 当前问题与对应改法

| 当前问题 | 对阅读的影响 | 本轮改法 |
| --- | --- | --- |
| 首页先展示工作经历，公司与任职信息占据入口 | 读者先进入履历，再寻找作品 | 删除首页工作经历表和按公司组织的作品板块；项目仅保留个人参与范围 |
| 总首页、项目首页和详细文档多次重复概述 | 阅读变长，新增信息不清楚 | 约定每层职责，每类详细事实确定一个主要承载位置 |
| 企业资产与个人作品的公开范围不同 | 不能使用同一原件展示标准 | 企业实践只保留允许公开的参与事实与个人判断，权限不明内容先撤下 |
| 项目规划与历史实践混在主阅读路径 | 容易把拟做功能当成已交付 | 历史案例居前；规划放后并标明状态，保留有价值的产品设计 |
| 重要数字的来源强度不同 | 读者需要翻多层才能知道统计范围 | 建立可公开的主张索引，显示层就近说明必要口径；非公开核验资料放在仓库之外 |
| 维护文档仍沿用三项目和私有阶段的描述 | 后续维护容易引用过期规则 | 更新维护入口，给旧计划标注历史身份；保留历史记录 |

### 4.2 每个作品入口包含什么

个人 / 研究作品包含名称、实际问题、核心机制、真实阶段、预览与直接入口。两个企业实践只保留名称、个人职责和通用判断的文本入口，不要求产品界面或机制预览。个别项目可用双图说明必要的前后变化，避免把复杂架构图压成看不清的缩略图。

总首页中文正文先以约 1,400–2,200 字符为编辑参考，最终以内容完整和实际可读为准，不机械凑字数。每项说明约 80–160 字，详细指标和技术参数交给项目页。

GitHub README 采用单列连续作品区块和普通锚点目录。避免依赖自定义 CSS、复杂卡片布局或大宽表格；窄屏也应能正常阅读。

### 4.3 删除、移动和保留

- 删除：工作经历表、任职时间轴、按公司划分的两个入口区域、重复产品总表。
- 删除：泛化能力自评、岗位匹配说明、求职推荐阅读表。
- 保留必要的个人参与和贡献范围，通常一至三句；两个企业实践不出现公司名称。
- 保留：真实产品图、实机画面、交付样例、研究结果，以及直接体验入口。
- 精简：每个作品只保留一项必要成果或阶段说明，不把首页写成数字汇总榜。
- 沿用：当前首页不展示个人姓名的做法，不新增联系方式或身份口号。

候选开场文案仅作为结构示意，实施时再编辑：

> 围绕真实任务，记录 AI 工作流、应用、开发者平台与预测研究中的产品设计、工程交付和验证过程。

## 5. 项目页的共同阅读逻辑

个人与研究作品沿“问题 → 方案 → 交付 → 验证 → 迭代”阅读，不要求相同章节。企业实践另以允许公开的参与事实、职责、个人判断、历史阶段和披露边界验收，不能用企业原件补齐展示。

1. **概览与范围**：是什么、为谁解决什么问题；用简短背景说明个人责任、合作与阶段。
2. **先看作品**：尽早出现截图、产物、机制图或研究结果，附清楚说明与直接入口。
3. **一次具体任务**：输入是什么，用户或研究者如何操作，系统交付什么，在哪里修改或判断。
4. **关键决策**：选择两三项真实取舍，说明约束、备选、选择、代价与结果。
5. **交付与验证**：列出已有结果，以及方法和使用范围；让失败分析接回实际决策。
6. **迭代与继续查看**：简述尚未解决的问题，链接完整设计、证据、运行说明和后续规划。

项目首页先以约 1,000–2,000 中文字符为参考；内容 Agent 等多路径项目允许适度增加。重要技术设计继续进入主叙事，不因压缩字数而只剩宣传摘要。

每项详细事实确定主要位置：README 摘要链接过去，其他页面不再完整复述。首页中的结果写到结论即可，分母、计算和逐例结果放评测页。入口不要求先安装环境、运行脚本或阅读源码。

## 6. 六个项目逐项改版

### 6.1 Multi-Skill Content Agent

**作品主线**：创作者从已有素材出发，按任务取得可修改、可取用的内容交付；共同分析减少重复理解，文件与人工确认承担路径交接。

| 文件 / 材料 | 具体动作 | 完成条件 |
| --- | --- | --- |
| README.md | 删除与下层重复的长篇阶段路线和未来商业规划；用简短架构说明四条独立路径；提前放代表产物 | 能看懂整体作品及四类任务，首页不再长篇展开所有任务细节 |
| README.md 的四类任务 | 各保留简短的输入、交付、关键变化和真实结果；四类路径都提供清楚入口 | 不因首页精简而隐藏某条路径或把雷达描写成统一平台入口 |
| docs/case-study.md | 主体由未来扩张规划调整为已有决策的复盘：共享分析、部分调用、版本对齐、事实核验 | 每个关键决定能链接实际任务或实现；现有需求池和商业规划留作明确标注的后续部分 |
| docs/architecture.md | 保留实际技术细节；核对图和正文是否对应当前源码 | 区分宿主 Agent 能力、自有脚本、未接入扩展 API；准确描述回退与重试 |
| demo/README.md 及四类案例 | 作为完整产物入口；检查输入、修改与输出的链接 | 六图、演示、发布文案、封面、产品稿与雷达报告可直接查看 |
| evaluation/ | 保留日志、构造探针、尺寸检查、失败记录 | 不把文件通过当质量通过，不把模型审稿当人工采纳 |

重点展示三个设计：共享分析与分别表达；按需取用与改稿后对齐；程序状态、事实质量与人工采用分别判断。语义事实校验、统一任务记录、预算控制等未完成部分继续标为规划。

“50+ 次”“Token 约降 60%”“约 3 小时到 10 分钟”分别核对范围。有可解释的历史比较条件但原件不完整时，可以在案例中作为明确限定的个人回顾估计；比较对象、任务、计时或用量条件无法确定时，首页撤下相应精确百分比和时间对照，改用可证明的产物、机制与交付范围。具体项目页也不能仅加“个人总结”便继续作客观业绩陈述。新增评测不作为历史幅度的证明。

六张历史原图的规格缺口保留。若后续补做裁切，作为新增派生版本保存，注明处理日期和方式，不替换历史原件或声称当时已完成。

**验收**：能沿一条路径从真实输入看到修改、交付和检查；四条路径关系准确；作品首页缩短后仍保留技术判断。

### 6.2 StayWord

**作品主线**：把录音变成能阅读、回查和复用的笔记，在端侧资源约束下完成产品交付与反馈迭代。

| 文件 / 材料 | 具体动作 | 完成条件 |
| --- | --- | --- |
| README.md | 概览之后优先展示转写回听、摘要和导出；保留完整任务的简短说明 | 读者先看到实际应用，再进入模型与工程 |
| docs/product-discovery.md | 主要承担问题定义、MVP 和实际版本演进 | 不与 case-study 重复展开相同决策 |
| docs/case-study.md | 聚焦本地推理、摘要失败保留转写、反馈驱动倍速与分类型导出 | 每项体现具体选择与代价，并链接实现或反馈 |
| docs/technical-design.md | 保留架构、模型、调度、恢复和跨端差异 | iOS 与 Android 的实现和实测范围分别清楚 |
| docs/metrics-and-experiments.md | 历史成果与已有数据居前，待部署指标和情景分析下沉到后续部分 | 不把情景测算当实际用户表现 |
| demo/、evaluation/ | 继续保留录屏、版本、模型诊断和工程结果 | 实机录屏、Mac 模型诊断、模拟器测试分别标明 |

48 次模型诊断保留为一次具体的采用决策，避免让失败评测压过整个应用体验。Top 10 补地区、日期及可核查材料；在补齐前明确来源与缺失范围。

真机质量、长录音耗时、恢复行为和用户复用属于产品后续验证。现有待测表可以保留，不作为本轮文案改版已经完成的结果。

**验收**：能看懂一次录音如何变成笔记、用户如何回查、为什么选择本地处理、反馈怎样影响版本。

### 6.3 企业创作实践：有限公开复盘

只保留允许公开的创作者任务、个人职责概括与产品方法。通用分析需明确是个人思考，不能写成某个内部功能、流程或结果已经实际交付。不公开企业素材、源码、截图、原型、工作流配置、合作信息或经营指标；不通过重绘与模拟复原内部设计。

前轮机制图、具体实现描述和企业原件补证要求撤销。缺少公开授权不是材料缺口；项目当前是否在线不作断言。若基本参与事项的公开范围仍不明确，或删减后没有独立阅读价值，就从公开入口撤下。

**验收**：参与与职责不扩大，公开范围明确，个人通用方法与特定历史交付分开。不要求企业产物或业务数据证明，也不将无法公开原件判为案例未完成。

### 6.4 企业开发者实践：有限公开复盘

只在允许范围讨论开发者任务、协作困难及个人产品判断。撤下可能复原内部流程、系统实现和交付机制的图文，以及业务统计、具体任务资料与内部案例细节。

前轮图示与原件验收要求撤销。不补源码、运行记录、审核材料或模拟内部界面。独立方法可以讨论，但不冒充已实施的企业方案；当前服务运行状态未知时，不写成仍在线。

**验收**：公开参与事实与职责准确，通用判断具有阅读价值，未知披露范围的具体内容已经移除。不能在此范围内形成有意义复盘时，撤下公开入口，不影响其他四个作品。

### 6.5 RiverSR

**作品主线**：在不同使用条件下建立预测基线，通过隔离验证、误差诊断和配对实验决定模型的用途与下一步投入。

| 文件 / 材料 | 具体动作 | 完成条件 |
| --- | --- | --- |
| README.md | 用非专业语言说明预测任务、实际交付和两个关键判断 | 先理解研究问题，再阅读指标和算法细节 |
| demo/README.md | 保留真实结果图、单站回放、模型与数据入口 | 能从一个站点追到输入、验证与使用判断 |
| docs/decision-timeline.md | 作为深入阅读的主要决策路径 | 呈现实验为什么改变方向，压缩重复结果陈述 |
| docs/case-study.md | 明确承担研究使用场景与应用规划，调整页面标题和链接文案 | 不把后续应用流程写成已有用户实践 |
| docs/technical-design.md | 保留训练、资源、冻结、恢复与交付细节 | 深入阅读仍能查到完整工程判断 |

**验收**：非领域读者能理解“模型交付了什么、何时可用、什么情况下仍失败、证据怎样改变投入”。

### 6.6 PriceMap AI

**作品主线**：把分散的服务报价组织成可发现、可解释、可回查的信息工具，并在更新成本与数据质量之间作取舍。

## 7. 证据与成果数字的整理方法

### 7.1 公开索引与私有核验资料的边界

实施阶段新增一份轻量 `.maintenance/CLAIMS_REGISTER.md`，作为可公开的编辑索引，只记录可以公开的主张、统计范围、证据类型、来源说明、公开依据链接、可用表述与待补状态。它不替代项目内的证据解释，也不承载非公开原始资料。

本仓库目前公开，`.maintenance/` 及点号目录名不提供访问保护；一旦提交并推送，其中内容同样可被访问。企业内部统计底稿、未公开业务文档、合作方信息及其他非公开核验资料保留在本仓库和 Git 工作树之外的私有位置。仓库内只保留可公开的来源描述与核验状态，不写私有文件路径、访问地址或原件内容；不能把“原件未公开”误记为“已经核验”。

已公开不等于有公开授权，重绘、脱敏或模拟也不自动改变披露范围。发布前检查企业相关正文、维护资料与待提交差异；权限不明的具体内容先从公开版本撤下，不以“待确认”继续展示。企业原件不再列为应收集的补证材料。此项检查针对实际改动，不扩展为与本轮无关的历史全仓审计。

### 7.2 数字展示的准入条件

先区分三种情况，再决定首页与案例中的写法：

| 历史依据状态 | 首页与案例的处理 |
| --- | --- |
| 来源与统计 / 比较条件能够核对 | 可以展示，保留必要的范围限定并指向可公开的依据说明 |
| 历史条件可解释，但原件不完整 | 案例中可保留明确限定的个人回顾估计，说明比较范围、缺失和局限；首页是否保留取决于能否用短句准确表达依据强度 |
| 统计对象、周期或历史比较条件无法确定 | 首页撤下对应精确业绩数字，展示已确认交付；案例中不作为客观成果突出，公开索引仅记录待补状态 |

“个人使用总结”不能让缺少比较条件的精确百分比自动成立。个人与企业数字都先判断是否允许公开，再判断统计依据。没有公开权限的企业数字直接撤下，不以来源说明或回忆形式继续保留。私有依据即使有效，也不意味着可以公开原件；按允许公开的口径描述核验范围即可。

按六类事实分别处理：

| 类型 | 写法 |
| --- | --- |
| 原始产物、日志或测量支持 | 写清对应版本、分母、时间与方法，链接直接依据 |
| 本人补充确认的历史事实 | 如实说明来源；数字需满足上表准入条件，不能仅凭“本人确认”省略关键统计范围 |
| 事后复盘或重绘 | 标注复盘日期与依据，不伪装成历史设计原稿 |
| 新增实验结果 | 写明新日期和条件，回答这次实验实际能回答的问题 |
| 构造样本、情景估算 | 就近标明构造 / 假设，不能换名为生产准确率或经营成绩 |
| 尚未完成的计划 | 使用待验证表述，不混入成果清单 |

优先核对以下主张：

| 主张 | 需要补清楚的内容 | 完成前如何处理 |
| --- | --- | --- |
| 内容生产 50+ 次 | 时间、任务范围、一次运行的定义 | 按个人累计使用总结说明，不推导统一成功率 |
| Token 约降 60% | 原方案、任务可比性、模型、usage 与失败成本 | 条件可解释时才保留限定的回顾估计；无法确定历史条件时撤下首页精确百分比 |
| 3 小时到 10 分钟 | 是否包括人工、生成、修改与等待 | 条件可解释时说明计时与任务范围；无法确定时撤下首页精确对照 |
| StayWord Top 10 | 地区、日期、类别与原始凭据 | 保留本人确认来源与缺失范围，不用 #54 / #60 窗口采样推算 |
| RiverSR 后期研究结果 | 执行回报与可重算原件的对应范围 | 明确目前收录材料层级 |
| PriceMap 报价规模与可比性 | 快照日期、资格筛选与多来源可比组 | 目录覆盖和严格比较分别呈现 |

如需新做两三次同类任务对照，只能验证当前条件下的效率与质量。历史“下降约 60%”是否成立，仍需当时基线或可解释的历史记录，不能由新实验倒推。

## 8. 视觉、链接与素材规则

1. 个人与研究作品使用最能解释作品的真实产物；企业实践不以重绘复原内部设计。
2. 每张图说明它是什么、来自何时、能证明什么。历史实拍、产物使用画面、机制示意和合成原型使用准确名称。
3. 架构和机制图优先采用可编辑 SVG 或 GitHub 能正常渲染的 Mermaid；不为展示制造虚构 UI。
4. 图片保持原始比例；缩略图可点击查看完整图；长图在适当位置分段或提供原图入口。
5. 视频提供可辨认的预览图和清楚的播放 / 下载入口；需要实际检查 GitHub 对现有媒体的呈现，不预设点击即流畅播放。
6. HTML 演示保留现有文件和截图入口，注明本地播放方式；主阅读路径不依赖先下载 HTML。
7. 不在本轮新增独立网页作品集、托管服务或复杂播放器。现有项目内 HTML 不因总首页改版而删除。
8. 新图放到对应项目目录；图文旁保留必要来源和版本，减少只有维护者能理解的编号。

## 10. 执行顺序与每阶段交付

### 阶段 A：内容盘点与证据映射

**执行约束**：复用已有材料、来源记录和核查结果，仅补足支撑本轮实际改版的简明清单，不对六项目重新做全面审计。只在发现新矛盾、计划使用新主张或对应文件发生变化时定点核对。现有计划已经列出的文件动作直接沿用，不再生成一套重复规划文档。

- 为六个作品各写一句准确定位、当前阶段与代表产物。
- 建立主张清单，标明可直接修改内容与需要补充的事实。
- 梳理各页面重复内容，指定每类信息的主要承载文件。
- 企业部分只确认可公开的名称、参与事实与职责范围；不收集企业原件或业务底稿。

**交付**：在现有进度记录中用一个简表标明六项目定位、代表素材、下一步和依赖；另建一份轻量公开主张索引。文件动作沿用本计划，待补问题按项目集中列在上述记录中，不拆成多份管理文件。具备改版所需信息即进入阶段 B；此阶段不重新训练或执行生产采集。

### 阶段 B：首页与一个项目样板

- 用现有素材重写总 README，删除首页履历和重复总表。
- 先以 StayWord 完成一个项目页样板：实际产品、完整任务、三个关键决定、验证与深入入口。
- 检查总首页与样板的桌面和窄屏 GitHub 阅读效果。

**交付**：可直接阅读的首页与 StayWord 样板。样板用于验证信息层级，不强迫其他项目采用相同长度、截图数量或章节。

### 阶段 C：企业实践的公开边界

撤下未经明确授权的具体机制、业务数据、合作信息及三张重绘图。取消此前企业原件补证和完整交付链验收；允许公开且有独立阅读价值的实践可保留，否则撤下入口。真实性、可公开性与展示价值分别判断。

**交付**：具体的保留 / 修改 / 撤下清单，最新公开版本与维护资料一致，历史风险检查明确范围。历史不未经评估重写；不以当前文件删除冒充历史清除。

### 阶段 D：调整其他三个项目

- 内容 Agent 精简重复规划，保留四类真实交付与技术设计。
- RiverSR 强化研究问题、采用决策和真实结果阅读路径。
- PriceMap 聚焦双路径查询、数据机制和当前比较能力。

**交付**：六个作品入口与深入文档的阅读职责统一，项目特点与技术深度保留。

### 阶段 E：全仓库核查与收尾

- 更新维护入口、历史标注、来源当前概述与本轮进度。
- 检查相对链接、章节锚点、图片、视频、HTML 和体验入口。
- 对照主张清单检查数字、版本、日期和状态一致性。
- 检查企业案例实际改动中的文字、图片、元数据与待提交差异；公开索引和案例不得带入非公开原始核验资料。
- 查看真实 GitHub 桌面呈现及窄屏阅读；本地近似渲染与真实远端验证分别记录。
- 执行 §11.3 的分层阅读测试，记录选择的项目、问题、观察到的结果与待改处；自查和独立读者测试分别说明。
- 只对实际改动的脚本或实现执行相关测试，保留现有运行证据；纯文案改版无需重跑重型模型或双端全量测试。

**交付**：最终差异、实际检查结果、尚缺材料及其影响。推送、远端元数据和任何部署分别记录范围与结果，不把本地编辑称为已上线。

### 独立队列：产品验证与功能改进

下列工作有独立方法和投入，不与页面改版混算：内容工作流质量与效率对照；StayWord 固定音频 / 真机 / 用户任务验证；PriceMap 严格可比覆盖和标签修复；RiverSR 后期原件补录与应用验证。

页面结构和已有事实的改版可以先交付，尚未完成的产品工作继续保持明确状态。不能靠新增说明文字将这些缺口标为解决。

### 11.3 从读者视角执行阅读测试

以下时间是测试目标，用来检查信息层级，不表示招聘方一定会投入这些时间，也不是承诺所有读者都能在时限内理解。

| 目标 | 测试方法 | 通过条件 |
| --- | --- | --- |
| 约 30 秒：首页识别 | 只浏览首页，回答六个作品分别是什么、有什么入口、目前处于什么阶段 | 能区分可体验应用、已交付流程、原型与研究；不需先读工作经历或源码 |

| 约 10 分钟：深入检查 | 选择一项具体结论，跟随链接进入设计、演示、评测或代码，解释依据与限制 | 能定位支持材料、对应版本与关键限制；不因重复描述或断链丢失证据路径 |

先做记录清楚的阅读自查；有实际独立读者时补充其观察。没有独立读者参与，不能把助手自查写成用户测试通过。首页识别覆盖六项；个人与研究作品的三分钟自查覆盖每项，十分钟深入至少覆盖工作流与研究结论。企业实践检查参与事实、方法思考与披露边界，不追查企业原件；被撤下的入口不参加作品完整度验收。
